## 1. 实际分层与依赖关系

### 1.1 三层实际职责

```
com.createpen.fifteenhundun
├── common/            无状态工具、常量、异常、上下文、配置
│   ├── anno/          @AutoFillTime @AutoLog @RateLimit @RequireRole
│   ├── config/        Redis / CORS / Async / Mail / WebSocket
│   ├── constant/      Redis key、状态码、模块名、邮件文案
│   ├── context/       BaseContext（ThreadLocal: id + username）
│   ├── exception/     GlobalExceptionHandler + 9 个自定义异常
│   ├── response/      Result<T>
│   └── util/          JwtUtil PasswordUtil IpUtil AliOSSUtil FileUploadValidator RandomCodeUtil
├── framework/         请求生命周期上的横切设施
│   ├── aspect/        AutoFill / AutoLog / RateLimit / RoleCheck
│   └── interception/  LoginFilter（Servlet Filter）、CurrentSqlInterceptor（MyBatis 插件）
└── module/
    ├── auth/          登录 5 种方式 + 登出 + 验证码
    ├── user/          注册、资料、头像、删除；**feedback 也塞在这里**
    ├── admin/         用户管理、邀请码、分页缓存、日志查询
    └── article/       仅剩一个孤儿 XML（Java 侧已删）
```

依赖方向基本是 `module → framework → common → (Spring/JDK)`，但有 4 处反向或越界，需要在改造时顺手掰正：

| 位置 | 问题 |
| --- | --- |
| `framework/aspect/AutoLogAspect` | 直接依赖 `module.user.mapper.CommonMapper`，横切层反向依赖业务层 |
| `framework/aspect/RoleCheckAspect` | 直接依赖 `module.user.mapper.UserMapper`，同上 |
| `module/admin/service/impl` | 用 `module.user.mapper.AdminMapper`，admin 的 Mapper 却放在 user 包下 |
| `module/user` | 同时承担"身份认证 / 用户资料 / 账号删除 / 头像存储 / 反馈"5 类职责，`UserServiceImpl` 已 351 行 |

这正是"不要再往 UserServiceImpl 里堆"的根因：**不是人懒，是包结构本身没有给出放的地方**。所以阶段 1 的第一步必须是切包，而不是加功能。

### 1.2 横切能力清单（14 项）

统一响应 `Result` ｜ 全局异常映射 ｜ JWT 签发/解析 ｜ Redis token 吊销 + 故障降级 ｜ `@RequireRole` 角色校验 ｜ `@RateLimit` 固定窗口限流（IP + 账号双维度） ｜ 客户端 IP 防伪 ｜ 上传白名单 + 图片魔数校验 ｜ OSS 单例客户端 ｜ 密码 bcrypt ｜ 邮箱验证码（恒定时间比较） ｜ 操作审计 `@AutoLog` ｜ 时间字段自动填充 ｜ 异步双线程池（`emailExecutor` / `generalExecutor`）

这 14 项里，**12 项可以直接用，2 项（响应、鉴权）需要改造**。

## 3. 必须改造（方案 + 工作量）

### R1 鉴权双通道（匿名浏览 + 登录下载）· 2 人日

**现状**：`LoginFilter` 是 `@Component Filter`，对**所有** URL 生效；`SKIP_URIS` 只有 `/user/login`（全部方法）与 `POST /user/register`。除此之外一律 401。

**方案**（不引入第二套安全框架，仍是 Filter + Interceptor + 切面）：

1. **Filter 降级为"解析器"**：只做三件事 —— CORS 预检放行、解析 token（有则验签+验 Redis+查状态，无则跳过）、`finally` 清理上下文。**不再做拒绝决策**，也不再因 token 过期而阻断公开页。
2. **新增 `AccessControlInterceptor`（`HandlerInterceptor`）做"决策"**：能拿到 `HandlerMethod`，直接读注解，比字符串前缀匹配可靠：
   - `@PublicApi` → 任何人可访问（无 token 也放行；带**无效** token 时按匿名处理，不 401，避免用户 token 过期后连首页都看不了）
   - 无注解 → 必须有登录态，否则 401
   - `@RequireRole(...)` / `/admin/**` → 必须有角色，否则 403
3. **默认拒绝（fail-closed）**：新增接口忘记标注 = 需登录。杜绝"新加的 `/admin/xxx` 忘了加白名单"这类事故。
4. **匿名语义纠正**（关键）：删除 `BaseContext.setCurrentId(0L)` / `setCurrentUsername("login")` 的假身份。改为 `CurrentUser{ id=null, username=null }` + `BaseContext.isAnonymous()`。理由：`0` 会被 `RoleCheckAspect` 的 `currentId <= 0` 判成"未登录"（碰巧对），但会被 `updateAvatar` 当成合法 userId，也会让 `FeedbackServiceImpl.addFeedback` 拿 `id=0` 查用户得到 null 再 NPE —— **是静默错乱，不是报错**，比报错危险。
5. **改造后必须跑三态矩阵**（匿名 / 登录普通用户 / 管理员）×（公开页 / 下载 / 提交插件 / 后台），共 12 个用例，全部纳入自动化测试。

**顺带解决**：`OPTIONS` 预检目前"带 Origin 才放行"，改造后由 CORS 过滤器统一处理，移除这个特例。

### R2 权限校验位置上移 · 0.5 人日

**现状**：`FeedbackServiceImpl` 把 `@RequireRole` 打在 **Service 实现类方法**上。Spring Boot 3 默认 CGLIB 代理所以生效，但一旦有人配 `spring.aop.proxy-target-class=false` 切成 JDK 动态代理，注解就**静默失效**，结果变成"任何登录用户可读全站反馈"。

**方案**：权限注解只允许出现在 Controller 层；Service 层用 `BaseContext` 做二次断言（`assertAdmin()`）。同时把 `/admin/**` 前缀规则保留在前缀层做兜底，形成三层：前缀 → 注解 → 服务内断言。

### R3 数据库重建（schema-only）· 1 人日

**现状**（已逐行核实）：`file/hundun.sql` 228 行里塞了 1 条 article、1 条 feedback、**1 行 274KB / 934 条 operation_log**、以及 `users` 表的真实用户行（bcrypt `$2a$12$...` 哈希 + `@gmail.com` / `@outlook.com` 邮箱 + 手机号）。另有 `article` / `article_comment` / `memo` 三张历史表。

**方案**：

- `db/01_schema.sql`：只保留 DDL（users / feedback / operation_log + 新业务表），无任何 INSERT
- `db/02_seed.sql`：仅字典与种子内容（HundunDesktop 软件 + 一个版本 + 资产元数据 + 内置插件 ID 保留列表），**零用户行**
- `db/03_plugin_spec.sql` 起的增量脚本：每条 `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 风格，可重复执行
- 管理员账号不写死哈希，改为启动引导：`ADMIN_BOOTSTRAP_USERNAME/PASSWORD` 存在且库中无管理员时创建（幂等），否则跳过
- 现有 `users` / `feedback` 表结构**原样保留**，不改字段语义（约束 3）

### R6 启动硬依赖解开 · 0.5 人日

**现状**：`JwtUtil`、`MailProperties`、`AliOSSUtil` 的构造器都 `throw IllegalStateException`。缺 `MAIL_AUTH_CODE` 或 OSS AK/SK 时**应用起不来**。后果：CI 无法跑测试，新同事拉代码必须凑齐 3 套密钥才能 build。

## 5. 两项必须现在定的方案

### 5.1 双语方案：**双层拆分，错误码优先**

**决定**：

| 文案层 | 归属 | 机制 |
| --- | --- | --- |
| 界面文案 | 前端 | `vue-i18n` + `locales/{zh,en}.json`，key 按页面命名空间分组 |
| 内容文案（软件介绍、插件说明、版本记录） | 数据库 | `*_zh` / `*_en` 成对字段；API 按 `lang` 只返回一份，后台接口返回全量供编辑 |
| 后端提示语 | **码值** | `Result.code` 用稳定业务码（如 `DOWNLOAD_ASSET_NOT_FOUND`），前端 `code → i18n key` 映射；后端 `message` 仅作中文兜底，**不用于展示** |

**为什么不做"后端按 Accept-Language 返回文案"**：动态拼接的消息（"文件大小不能超过 {x}MB"、"版本 {v} 已下架"）后端一旦生成成自然语言，前端就无法再翻译，切换语言后必然残留。码值方案是唯一能通过"切换后零残留"验收的做法，且天然支持日志、监控按码聚合。

**兼容历史异常**：不重写 321 处中文。做法是给每个自定义异常挂一个 `ErrorCode`，`GlobalExceptionHandler` 输出码 + 中文兜底 message；前端映射表未命中时显示"操作失败，请稍后再试 / Something went wrong"，**永不显示后端中文**。工作量从"改造 321 处"降到"加 15 个枚举 + 一张映射表"。

**语言路由**：`/zh/...` `/en/...` 前缀（不是 `?lang=`），根路径 `/` 按 localStorage → `Accept-Language` → 默认 `zh` 重定向。理由：①SEO 需要独立 URL 与 `hreflang`；②分享链接能保持语言；③持久化用 localStorage，切换即时生效。

**强制约束**（防"后面再抽"）：
- `scripts/check-i18n.mjs`：扫 `src/**/*.vue|js`，任何组件内出现 CJK 字符即失败（`locales/` 与注释白名单除外）
- 同一脚本校验 `zh.json` / `en.json` key 集合完全一致
- 验收时对 en 路由跑一遍 CJK 扫描，作为"无残留"的客观证据

### 5.2 SEO 方案：**不做 SSR，History 路由 + 预渲染快照**

**决定**：

1. 阶段 1 就用 `createWebHistory` + 语义化结构（`<h1>`、`<article>`、面包屑），每个软件/插件一个稳定 slug URL，**不用 hash 路由**（否则后续无法平滑加预渲染）。
2. 动态 meta：`useHead` 管理 `title/description/OG/canonical/hreflang`，数据来自 API。
3. 后端动态输出 `/sitemap.xml`（列全部已发布软件与插件）与 `/robots.txt`。
4. 阶段 1 末补 **构建期预渲染快照**：Node 脚本先请求 `/api/sitemap` 拿到全部 slug，再用无头 Chromium 访问每个路由、落盘静态 HTML，部署时与 SPA 并存（`try_files $uri $uri/ /index.html`）。数据更新后触发一次重建。

**为什么不做 SSR**：SSR 需要在 Node 端跑同一套组件并处理数据预取，等于引入"第二套运行时"，违反"不换技术栈/不引入第二套后端"。而本项目内容更新频率低（发版才变），构建期快照足以覆盖，成本低一个数量级。

**退路**：若你不接受 puppeteer 作为构建依赖，则只交付 1–3（静态 meta + 动态 sitemap），收录会慢一些但不阻塞上线。**我建议按 1–4 做，pre-render 单独一个提交，可随时回退。**

### 6.2 下载链路（登录 + 私有桶 + 预签名）

```
前端点击下载
  → POST /download/software/{assetId}/ticket      （需登录，@RateLimit 30/时/账号 + 60/时/IP）
  → 后端校验 asset 已发布 → 生成 OSS 预签名 URL（TTL 5min）
      → 同步：release_asset.download_count += 1（原子）
      → 异步：写 download_record（generalExecutor）
  → 返回 { url, expiresAt, fileName, fileSize, sha256 }
  → 前端校验 sha256 展示 + window.location = url（浏览器直连 OSS，不经应用服务器）
```

**为什么用票据而不是直接 302**：302 无法区分"准备中/失败/超频"，也不能返回 sha256 供前端校验；票据还便于埋点与后续换 CDN。**同时保留** `GET /download/software/{assetId}`（登录后 302）作为无 JS 场景的降级。

**桶必须是私有读**。如果桶公开读，URL 永久有效，"登录才能下载"就只是装饰。预签名是唯一能同时满足"直连 OSS/CDN"和"登录门禁"的做法。CDN 接入需配合鉴权 URL（后续阶段，预留 `cdnDomain` 配置项）。

### 6.3 插件 zip 校验（对齐桌面端安装器）

桌面端 `docs/PLUGIN_DEVELOPMENT.md` 已定死三条硬规则，服务端必须一致：

1. **ZIP 根目录直接含 `manifest.json`**，不能多套一层文件夹
2. 校验 `entry` 真实存在且以 `.html`/`.js` 结尾
3. 拒绝路径穿越；**拒绝覆盖内置插件 ID**

服务端校验清单：zip 魔数 `PK\x03\x04` → 条目数上限（≤2000）→ 解压总大小上限（≤50MB）与压缩比（≤100:1，防 zip bomb）→ 路径穿越（`..`、绝对路径、符号链接）→ manifest JSON Schema（`id` 正则 `^[a-z0-9][a-z0-9-]{0,63}$`、`name ≤32`、`version` 语义化、`windowSize` 200–4000、`platforms ⊆ {win32,darwin,linux}`、`permissions ⊆ {storage,messaging,notifications,clipboard}`）→ `id` 全局唯一 → `id` 不在内置保留列表（`calculator`/`fast-txt`/`task`/`fast-cmd`）。

校验器与桌面端 `src/main/plugin-installer.js` 的规则一一对应，写成单元测试逐条覆盖。
